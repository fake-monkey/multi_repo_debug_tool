# `repo_debug` 发布计划

## 当前状态

本计划已经确定，尚未实施。当前不创建发布脚本、不生成 Scoop manifest、不创建 Gitee Release，也不执行 Git 提交或推送。

## 目标

为 `repo_debug` 建立一套由本地 PowerShell 脚本发起的发布流程：在父仓库的 Cargo workspace 中完成 Windows 可执行文件构建，在本子仓库中维护发布脚本和 Scoop bucket，通过 Gitee Release 分发压缩包，并让 Scoop 用户能够直接把本仓库作为 bucket 源使用。

## 仓库职责边界

- `multi_repo_debug_tool` 子仓库负责：
  - 发布脚本 `scripts/publish-release.ps1`。
  - Scoop manifest `bucket/repo-debug.json`。
  - 版本号、README、CHANGELOG、Git 标签和 Gitee Release。
  - 发布产物的生成规则、校验值和上传。
- 父仓库 `toolbox` 只提供 Cargo workspace、`Cargo.lock`、共享依赖和构建输出目录。
- 发布脚本可以从子仓库定位父仓库并调用 Cargo，但不得修改、提交或推送父仓库。
- 原有的独立 `scoop_bucket` 仓库不参与 `repo_debug` 的发布。

子仓库产生新提交后，父仓库本地会显示 submodule 指针发生变化。这是 Git submodule 的正常行为，不代表发布脚本修改了父仓库。是否更新并提交父仓库中的 submodule 指针，由用户在发布流程之外单独决定。

## 固定发布约定

- 版本来源：子仓库 `Cargo.toml` 中 `repo_debug` package 的版本。
- Git 标签：`v<version>`。
- Windows 目标：`x86_64-pc-windows-msvc`。
- 发布压缩包：`repo_debug-v<version>-x86_64-pc-windows-msvc.zip`。
- 压缩包采用扁平结构，包含：
  - `repo_debug.exe`
  - `README.md`
  - `CHANGELOG.md`
- 下载地址固定为：

  ```text
  https://gitee.com/FakeMonkey/multi_repo_debug_tool/releases/download/v<version>/repo_debug-v<version>-x86_64-pc-windows-msvc.zip
  ```

- Release 标题使用版本标签，正文取自 `CHANGELOG.md` 中与当前版本对应的章节。
- 语义版本包含预发布标识时（例如 `1.2.1-alpha.1`），对应的 Gitee Release 标记为 prerelease。

## 发布脚本接口

计划在子仓库增加以下入口：

```powershell
.\scripts\publish-release.ps1
.\scripts\publish-release.ps1 -DryRun
```

脚本通过 `$PSScriptRoot` 定位子仓库，并由子仓库位置推导父仓库位置，不依赖调用命令时的当前工作目录。

正式发布前要求：

- 子仓库源代码、README、CHANGELOG 和版本修改已经提交并推送。
- 子仓库 `Cargo.toml` 中的版本在 `CHANGELOG.md` 中存在对应章节。
- 除发布脚本即将生成的 Scoop manifest 外，子仓库没有未提交改动。
- Gitee CLI 已安装并通过 `gitee auth login` 完成认证。
- 当前标签、Release 和同名附件不存在冲突。

## 正式发布流程

1. 校验子仓库状态、远端同步状态、版本、CHANGELOG 章节和 Gitee 登录状态。
2. 从子仓库发起父 workspace 构建：

   ```powershell
   cargo build --release --locked `
     --manifest-path <父仓库>\Cargo.toml `
     -p repo_debug
   ```

3. 从父仓库的 Cargo target 目录取得 `repo_debug.exe`，与子仓库的 `README.md`、`CHANGELOG.md` 一起打成固定名称的 ZIP。
4. 计算 ZIP 的 SHA256。
5. 生成或更新子仓库的 `bucket/repo-debug.json`，写入当前版本、固定格式下载地址和 SHA256。
6. 校验 manifest 是合法 JSON，并确认其 URL、版本和哈希与本次产物一致。
7. 只暂存 Scoop manifest：

   ```powershell
   git -C <子仓库> add -- bucket/repo-debug.json
   ```

8. 在子仓库创建提交并推送，提交信息为：

   ```text
   chore(release): update Scoop manifest for <version>
   ```

9. 以这个子仓库提交为目标创建 `v<version>` 标签和 Gitee Release，将对应 CHANGELOG 章节作为 Release 正文。
10. 上传已经构建并计算过哈希的 ZIP，随后重新查询 Release，确认标签、正文和附件均可访问。

发布脚本的 Git 操作必须显式使用 `git -C <子仓库>`，并且只允许暂存 `bucket/repo-debug.json`，不得使用会顺带暂存其他文件的命令。

## Scoop manifest 与使用方式

`bucket/repo-debug.json` 包含实际发布版本、对应下载地址和精确 SHA256，并保留固定的 `checkver` 与 `autoupdate` 规则：

- `checkver` 从 Gitee Release 列表读取最新标签并提取版本。
- `autoupdate` 按固定标签和压缩包命名规则推导新版本下载地址。
- 正常的 `scoop update` 只拉取 bucket 仓库提交，不会替代发布脚本计算并提交新 manifest 的版本和哈希。

首次安装：

```powershell
scoop bucket add repo-debug https://gitee.com/FakeMonkey/multi_repo_debug_tool.git
scoop install repo-debug/repo-debug
```

后续更新：

```powershell
scoop update
scoop update repo-debug
```

## `-DryRun` 行为

`-DryRun` 用于在真正发布前验证本地流程：

- 执行 release 构建。
- 生成 ZIP 并计算 SHA256。
- 生成 Scoop manifest 预览。
- 校验产物内容和 manifest 格式。
- 不修改受 Git 跟踪的文件。
- 不执行 Git 提交或推送。
- 不创建标签、Gitee Release 或远端附件。

预览文件和构建产物放在未受 Git 跟踪的发布输出目录中，正式实现时应确保该目录不会污染子仓库状态。

## 首次发布

首个计划发布版本为 `1.2.1-alpha.1`：

1. 在 `CHANGELOG.md` 中补充 `1.2.1-alpha.1` 章节。
2. 先提交并推送版本、CHANGELOG、README 和发布脚本等源文件修改。
3. 运行发布脚本完成构建、打包和哈希计算。
4. 由脚本生成第一份 `bucket/repo-debug.json`，只提交并推送该 manifest。
5. 在包含正确 manifest 的子仓库提交上创建 `v1.2.1-alpha.1` prerelease，并上传 ZIP。

这样无需预先提交包含占位哈希的 manifest，Release 标签对应的源码提交中也包含可直接使用的 Scoop manifest。

## 失败恢复与重复执行

- 构建、打包或 manifest 校验失败时，不创建提交和远端 Release。
- manifest 提交或推送失败时，不继续创建 Release。
- Release 创建成功但附件上传失败时，保留 Release；再次执行时复用版本一致的 Release 并补传附件。
- 已存在同名标签或 Release 时，必须确认其目标提交和版本与本次发布一致；不一致则终止。
- 已存在同名附件时，必须核对文件大小和哈希；一致则视为已经上传，不一致则终止并要求人工处理。
- 重复执行不得生成额外版本提交、重复标签或重复附件。

## 验收方案

发布脚本实现后按以下顺序验收：

1. 执行 `-DryRun`，确认 release 构建成功。
2. 检查 ZIP 名称和扁平目录结构，确认三个文件齐全。
3. 验证生成的 SHA256 与 ZIP 一致。
4. 验证 Scoop manifest 是合法 JSON，版本、URL 和哈希正确。
5. 完成首次正式发布，确认 Gitee Release 页面及附件下载地址可访问。
6. 在未安装该工具的 Scoop 环境中添加本仓库 bucket 并安装。
7. 执行以下命令确认程序能够启动：

   ```powershell
   repo_debug --help
   ```

8. 发布一个后续测试版本，验证 `scoop update` 和 `scoop update repo-debug` 能获取并安装新版本。

本发布功能不要求额外运行 Rust 测试，但必须通过 release 构建、产物检查、manifest 校验和真实 Scoop 安装验证。
