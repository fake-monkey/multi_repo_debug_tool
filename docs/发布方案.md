# `repo_debug` Stable / Alpha 发布方案

## 方案状态

本方案是 `repo_debug` 发布功能的实施基线。后续发布程序、Scoop manifest、README 使用说明和验收工作均按本文执行；若实现中发现 Scoop 或 GitHub 的实际行为与本文不符，应先修订方案再继续扩大实现范围。

发布程序、README 使用说明、`1.2.1-alpha.1` CHANGELOG、alpha manifest 和发布输出忽略规则已经实现。Scoop manifest 只放在本子仓库的 `bucket/` 目录；本地 `--dry-run` 只在终端显示 manifest 内容，不在 `.release/` 中另存副本。Git 标签和 GitHub Release 由首次正式发布产生。

## 目标与核心语义

为 `repo_debug` 建立一套由本地 Python 程序发起的 Windows 发布流程：在父仓库的 Cargo workspace 中构建可执行文件，在本子仓库中维护发布程序和 Scoop bucket，通过 GitHub Release 分发压缩包，并通过独立 manifest 提供 stable 与 alpha 两条更新通道。

本方案中的“同一时刻只能使用一个版本”是指：

- 用户始终通过唯一的 `repo_debug` 命令运行工具。
- 全局 `repo_debug` shim 同一时刻只指向 stable、alpha 或某个历史版本中的一个。
- stable、alpha 及其尚未清理的历史版本可以同时保留在 Scoop 安装目录中，用于快速切换和回退，但不会形成多个不同的 CLI 入口。
- 用户通过 `scoop reset` 明确选择当前生效的通道或已安装版本。

升级后不得自动执行 `scoop cleanup`。保留上一版本是快速回退能力的一部分；用户主动执行 cleanup 后，被删除的历史版本不再能够通过 `scoop reset` 恢复。

## Scoop 模型

Scoop 没有独立的 channel 抽象。本方案将 stable 和 alpha 表示为两个独立的 Scoop app：

命名固定为：基础名称使用 `repo_debug`，alpha 通道使用连字符追加 `-alpha`，即 `repo_debug-alpha`；这与版本号 `1.2.1-alpha.1` 中的预发布分隔方式保持一致。不得写成 `repo_debug_alpha` 或 `repo-debug-alpha`。

```text
bucket/
├─ repo_debug.json
└─ repo_debug-alpha.json
```

两者都发布同一个可执行文件并暴露同一个命令：

```text
repo_debug
  app identity : repo_debug
  channel      : stable
  command      : repo_debug

repo_debug-alpha
  app identity : repo_debug-alpha
  channel      : alpha
  command      : repo_debug
```

安装后的结构与入口关系如下：

```text
stable app: repo_debug
  apps/repo_debug/
    <stable-version-1>/
    <stable-version-2>/
    current -> <当前 stable 版本>/

alpha app: repo_debug-alpha
  apps/repo_debug-alpha/
    <alpha-version-1>/
    <alpha-version-2>/
    current -> <当前 alpha 版本>/

全局命令入口: shims/repo_debug.exe
  -> 由最后一次 scoop reset 的 app 或版本取得
```

`repo_debug-alpha` 只存在于 Scoop 包管理层。无论当前激活哪个通道，用户实际执行的命令始终是 `repo_debug`。

## 仓库职责边界

- `multi_repo_debug_tool` 子仓库负责：
  - 发布程序 `scripts/publish_release.py`。
  - stable manifest `bucket/repo_debug.json`。
  - alpha manifest `bucket/repo_debug-alpha.json`。
  - 版本号、README、CHANGELOG、Git 标签和 GitHub Release。
  - 发布通道判定、产物生成、校验值计算和上传。
  - stable/alpha 安装、切换、更新和回退的用户说明。
- 父仓库 `toolbox` 只提供 Cargo workspace、`Cargo.lock`、共享依赖和构建输出目录。
- 发布程序可以从子仓库定位父仓库并调用 Cargo，但不得修改、提交或推送父仓库。
- 原有的独立 `scoop_bucket` 仓库不参与 `repo_debug` 的发布。

子仓库产生新提交后，父仓库本地会显示 submodule 指针发生变化。这是 Git submodule 的正常行为，不代表发布程序修改了父仓库。是否更新并提交父仓库中的 submodule 指针，由用户在发布流程之外单独决定。

## 版本与通道规则

- 版本来源为子仓库 `Cargo.toml` 中 `repo_debug` package 的版本。
- 不含预发布标识的语义版本属于 stable 通道，例如 `1.2.1`。
- 带 `alpha` 预发布标识的语义版本属于 alpha 通道，例如 `1.2.1-alpha.1`。
- 发布程序必须解析并校验语义版本，然后只更新本次版本所属通道的 manifest。
- stable 发布不得修改 `repo_debug-alpha.json`，alpha 发布不得修改 `repo_debug.json`。
- 当前方案只定义 stable 和 alpha。无法明确归入这两个通道的预发布版本必须终止发布，不得自行归类。
- Git 标签统一为 `v<version>`。
- alpha 对应的 GitHub Release 必须标记为 prerelease；stable Release 不标记 prerelease。
- stable 的版本检测规则必须排除所有预发布版本，不能因为 alpha Release 更新而进入 alpha 通道。
- alpha 的版本检测规则只接受 alpha 版本，不能捕获 stable 或其他类型的预发布版本。

## 发布产物约定

- Windows 目标：`x86_64-pc-windows-msvc`。
- 发布压缩包：`repo_debug-v<version>-x86_64-pc-windows-msvc.zip`。
- 压缩包采用扁平结构，包含：
  - `repo_debug.exe`
  - `README.md`
  - `CHANGELOG.md`
- 下载地址固定为：

  ```text
  https://github.com/fake-monkey/multi_repo_debug_tool/releases/download/v<version>/repo_debug-v<version>-x86_64-pc-windows-msvc.zip
  ```

- Release 标题使用版本标签，正文取自 `CHANGELOG.md` 中与当前版本对应的章节。
- 已生效的版本号和标签是一次性的。当前版本对应的本地标签、远端标签或 GitHub Release 任一已经存在，都必须终止发布，不得直接覆盖、复用或补传同版本内容。操作者可以升级版本号；如果已有发布确认作废，也可以先删除该 GitHub Release 及对应的本地、远端标签后重试。

## Manifest 设计

### Stable manifest

`bucket/repo_debug.json` 只描述最新 stable 版本：

```json
{
  "version": "<latest-stable-version>",
  "url": "<stable-release-zip-url>",
  "hash": "<sha256>",
  "bin": "repo_debug.exe"
}
```

其 `checkver` 使用 Scoop 内置的 GitHub 模式；该模式只读取最新正式 Release，不把 prerelease 识别为 stable 更新。`autoupdate` 使用 GitHub Release 的固定附件 URL。普通 stable 用户执行 `scoop update repo_debug` 时，不得因为存在更新的 alpha Release 而进入 alpha 通道。

### Alpha manifest

`bucket/repo_debug-alpha.json` 只描述最新 alpha 版本：

```json
{
  "version": "<latest-alpha-version>",
  "url": "<alpha-release-zip-url>",
  "hash": "<sha256>",
  "bin": "repo_debug.exe"
}
```

其 `checkver` 读取 GitHub Releases API，并用正则只捕获 `X.Y.Z-alpha.N` 标签；`autoupdate` 使用 GitHub Release 的固定附件 URL。Scoop app 名称虽然是 `repo_debug-alpha`，但 `bin` 仍为 `repo_debug.exe`，不得另行暴露 `repo_debug-alpha` 命令。

两个 manifest 都只维护各自通道的最新版本，不维护完整历史版本列表。通道内部的快速回退依赖 Scoop 已经保留在本机的版本目录和 `scoop reset <app>@<version>`。

## 发布程序接口

子仓库提供以下入口：

```console
python .\scripts\publish_release.py
python .\scripts\publish_release.py --dry-run
```

只提供 Python 入口，不增加 `.ps1` 启动包装器。发布程序使用 `Path(__file__).resolve()` 定位脚本自身、子仓库和父仓库，不依赖调用命令时的当前工作目录。

程序优先使用 Python 标准库实现参数解析、路径处理、JSON 生成、ZIP 打包和 SHA256 计算，通过 `subprocess` 调用 Cargo、Git 和 GitHub CLI（`gh`），不引入仅供发布使用的第三方 Python 依赖。

正式发布前要求：

- 子仓库源代码、README、CHANGELOG 和版本修改已经提交并推送。
- 子仓库 `Cargo.toml` 中的版本在 `CHANGELOG.md` 中存在对应章节。
- 除发布程序即将生成的目标通道 manifest 外，子仓库没有未提交改动。
- Python 3、Cargo、Git 和 GitHub CLI 均可用，且已通过 `gh auth login` 完成认证。
- 当前版本对应的本地标签、远端标签和 GitHub Release 均不存在。

## 正式发布流程

1. 校验子仓库状态、远端同步状态、版本、CHANGELOG 章节和 GitHub CLI 登录状态；随后检查当前版本对应的本地标签、远端标签和 GitHub Release，任一已存在都立即终止，并提示升级版本号，或在确认已有发布作废后清理 Release 及对应标签。
2. 根据语义版本判定 stable 或 alpha，并确定唯一允许修改的 manifest 路径。
3. 从子仓库发起父 workspace 构建：

   ```powershell
   cargo build --release --locked `
     --manifest-path <父仓库>\Cargo.toml `
     -p repo_debug `
     --target x86_64-pc-windows-msvc
   ```

4. 从父仓库的 Cargo target 目录取得 `repo_debug.exe`，与子仓库的 `README.md`、`CHANGELOG.md` 一起打成固定名称的 ZIP。
   ZIP 条目使用固定时间戳和权限生成，避免相同内容因文件系统时间变化而产生不同哈希。
5. 计算 ZIP 的 SHA256。
6. 生成或更新本次通道对应的 manifest，写入当前版本、固定格式下载地址和 SHA256；不得修改另一通道的 manifest。
7. 校验 manifest 是合法 JSON，并确认版本、URL、哈希、`bin`、`checkver` 和 `autoupdate` 均符合本通道规则。
8. 只暂存本次生成的 manifest：

   ```powershell
   # stable
   git -C <子仓库> add -- bucket/repo_debug.json

   # alpha
   git -C <子仓库> add -- bucket/repo_debug-alpha.json
   ```

9. 在子仓库创建提交并推送：

   ```text
   chore(release): update Scoop stable manifest for <version>
   chore(release): update Scoop alpha manifest for <version>
   ```

   实际提交只使用与本次通道对应的一条消息。

10. 以该 manifest 提交为目标创建并推送 `v<version>` 标签，再通过 `gh release create` 创建 GitHub Release；对应 CHANGELOG 章节作为 Release 正文，alpha 使用 prerelease，stable 使用正式 Release。
11. 创建 Release 时由 `gh` 直接上传已经构建并计算过哈希的 ZIP。上传后重新查询 Release，并通过 `gh release download` 下载附件，核对文件大小和 SHA256；认证信息完全由 `gh` 管理，不由发布程序读取或保存令牌。

发布程序的 Git 操作必须显式使用 `git -C <子仓库>`，并且只允许暂存本次发布通道对应的一个 manifest，不得使用会顺带暂存其他文件的命令。

## 用户工作流

### 添加 bucket

```powershell
scoop bucket add repo_debug https://github.com/fake-monkey/multi_repo_debug_tool.git
```

### 使用 stable

首次安装：

```powershell
scoop install repo_debug/repo_debug
repo_debug --version
```

后续升级：

```powershell
scoop update
scoop update repo_debug
repo_debug --version
```

`scoop update` 更新 Scoop 及已添加的 bucket；`scoop update repo_debug` 只沿 stable manifest 更新，不进入 alpha 通道。

### stable 通道内回退

```powershell
scoop info repo_debug
scoop reset repo_debug@<已安装的-stable-版本>
repo_debug --version
```

回退目标必须仍然保留在本机。`scoop reset` 不会重新下载已经被 cleanup 删除的历史版本。

### 试用 alpha

```powershell
scoop install repo_debug/repo_debug-alpha
repo_debug --version
```

安装 alpha 时，Scoop 会为新安装的 app 创建 `repo_debug` shim，因此 alpha 会直接成为当前生效通道，不需要再执行 `scoop reset`。

### Alpha 通道内升级和回退

升级 alpha：

```powershell
scoop update
scoop update repo_debug-alpha
repo_debug --version
```

回退到本机保留的旧 alpha：

```powershell
scoop info repo_debug-alpha
scoop reset repo_debug-alpha@<已安装的-alpha-版本>
repo_debug --version
```

### 在 stable 与 alpha 之间切换

切回 stable：

```powershell
scoop reset repo_debug
repo_debug --version
```

切到 alpha：

```powershell
scoop reset repo_debug-alpha
repo_debug --version
```

两个 app 暴露同名 shim。安装或更新某个通道时，Scoop 会重新创建该通道的 shim，使它成为当前生效通道；在两个已经安装的通道之间切换时，使用 `scoop reset` 让目标通道重新取得 `repo_debug`。卸载当前通道后，如果仍需使用另一通道，也要对保留通道执行 `scoop reset` 以恢复入口。

## 清理与卸载

- 不得在 manifest、发布程序或升级说明中自动执行 `scoop cleanup`。
- 用户确认不再需要回退时，可以主动清理指定通道的旧版本；清理后只能在该通道仍保留的版本之间 reset。
- 卸载当前占用 shim 的通道后，如果另一通道仍然安装，必须对保留通道执行 `scoop reset`，重新建立 `repo_debug` shim。
- stable 与 alpha 共用的配置若存在版本迁移，必须保证向后兼容，或在发布说明中明确不可逆影响。`scoop reset` 只切换二进制和入口，不会回滚用户数据。

## `--dry-run` 行为

`--dry-run` 用于在真正发布前验证本地流程：

- 解析版本并显示判定出的 stable 或 alpha 通道。
- 执行 release 构建。
- 生成 ZIP 并计算 SHA256。
- 只生成目标通道 manifest 的预览。
- 在终端输出 manifest 预览及其正式路径，不写入 `bucket/`，也不在 `.release/` 中生成 manifest 副本。
- 校验产物内容、manifest 格式、通道过滤规则和下载地址。
- 不修改受 Git 跟踪的文件。
- 不执行 Git 提交或推送。
- 不创建标签、GitHub Release 或远端附件。

ZIP 等构建产物放在未受 Git 跟踪的 `.release/` 发布输出目录中。Scoop manifest 的唯一文件位置是受 Git 跟踪的 `bucket/`；只有正式发布才允许更新对应通道的 manifest。

## 首次发布实施

首个发布版本为 `1.2.1-alpha.1`，因此首次发布只建立 alpha 通道：

1. 在 `CHANGELOG.md` 中补充 `1.2.1-alpha.1` 章节。
2. 实现发布程序，并在 README 中写明 stable/alpha 的安装、切换、升级和回退方式。
3. 先提交并推送版本、CHANGELOG、README、发布程序和本方案等源文件修改。
4. 运行发布程序，确认版本被判定为 alpha，完成构建、打包和哈希计算。
5. 由发布程序生成第一份 `bucket/repo_debug-alpha.json`，只提交并推送该 manifest。
6. 在包含正确 alpha manifest 的子仓库提交上创建 `v1.2.1-alpha.1` prerelease，并上传 ZIP。
7. 在首次 stable 版本发布时再生成 `bucket/repo_debug.json`，不得提前提交带占位版本或占位哈希的 stable manifest。

## 失败恢复与重复执行

- 无法确定版本所属通道时立即终止，不构建、不修改 manifest。
- 当前版本对应的本地标签、远端标签或 GitHub Release 任一已经存在时，立即终止；不比较旧产物，也不直接覆盖、复用或补传。提示用户升级 `Cargo.toml` 版本号并补充对应 CHANGELOG，或者在确认已有发布作废后删除 Release 及对应的本地、远端标签。
- 构建、打包或 manifest 校验失败时，不创建提交和远端 Release。
- manifest 提交或推送失败时，不继续创建 Release。
- 标签已经推送但 Release 创建失败时，该版本仍视为已经占用。可以升级版本号重新发布；如果确认此次发布作废，也可以清理对应的本地、远端标签后重试。
- Release 创建后任何校验失败，都先保留现场供人工排查。确认作废后，可以删除该 Release 及对应标签，再用原版本重试。
- 未升级版本号且未完整清理已作废 Release 与对应标签时，重复执行同一版本必定报错，不生成额外 manifest 提交、重复标签或重复附件。
- 任何通道更新失败时，不得自动切换到另一通道。
- `scoop reset` 目标不存在时应明确提示该版本未安装或已被清理，不得声称已经回退成功。

## 验收方案

当前阶段只验收首个 alpha 版本 `1.2.1-alpha.1` 能否完成发布和下载：

1. 执行发布程序，成功构建并发布 `v1.2.1-alpha.1` GitHub prerelease。
2. 确认 Release 中存在 `repo_debug-v1.2.1-alpha.1-x86_64-pc-windows-msvc.zip`，且 `bucket/repo_debug-alpha.json` 已写入正确的版本、下载地址和 SHA256。
3. 在本机 Scoop 中添加或更新本仓库 bucket，并成功下载 alpha 包：

   ```powershell
   scoop bucket add repo_debug https://github.com/fake-monkey/multi_repo_debug_tool.git
   scoop download repo_debug/repo_debug-alpha
   ```

如果 bucket 已经添加，只需执行 `scoop update` 后再下载。Scoop 下载成功且哈希校验通过，即视为本阶段验收完成。

stable 发布、连续版本升级、stable/alpha 切换、历史版本回退、cleanup 和配置兼容性均不作为首次发布的验收条件，待具备相应版本和环境后再验证。本发布功能当前不要求额外运行 Rust 测试。

## 不采用的方案

- 不使用单一 manifest 同时承载 stable 和 alpha；单 manifest 只有一条当前更新轨道，容易把普通用户带入预发布版本。
- 不把 alpha 的 CLI 改名为 `repo_debug-alpha`；通道差异只存在于 Scoop app 名称中。
- 不在 manifest 中维护完整历史版本列表；快速回退使用 Scoop 本机已安装版本和 `reset`。
- 不在安装或升级后自动执行 cleanup；这会删除可供即时回退的旧版本。
- 不依赖 `repo_debug@<version>` 从远端任意安装历史版本作为主要回退方案；本方案的回退边界是本机尚未清理的已安装版本。
