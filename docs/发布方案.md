# `repo_debug` Stable / Alpha 发布方案

## 文档定位

本文记录 `repo_debug` 发布体系的设计原因、职责边界、长期约定和已知陷阱，不承担安装手册或逐步操作指南的职责。

- 用户如何初始化 Scoop、安装、升级、切换通道和回退，以 [README](../README.md) 为准。
- 发布程序当前支持的参数和实际执行细节，以 [`publish_release.py`](../scripts/publish_release.py) 及其 `--help` 输出为准。
- 已发布版本及其变化，以 [CHANGELOG](../CHANGELOG.md)、Git 标签和 GitHub Release 为准。
- Scoop 当前发布状态，以 `bucket/` 中实际存在的 manifest 为准；尚未发布的通道不提前提交占位 manifest。

本方案已经落地。本文不记录“当前发布到哪个版本”一类容易过期的状态快照，也不重复上述事实来源中的操作命令。

## 要解决的问题

`repo_debug` 位于 `toolbox` 的 Cargo workspace 中，但自身又是独立 Git 子仓库。发布流程需要同时处理 Windows 构建、GitHub Release、Scoop manifest、stable/alpha 通道和父子仓库边界。如果依赖人工串联这些步骤，容易出现以下问题：

- 构建产物、manifest 哈希和实际上传附件不是同一份内容。
- alpha Release 被 stable 用户误识别为升级目标。
- 发布只完成一半，随后又用同一版本覆盖或补传，无法判断远端到底对应哪个提交。
- 发布程序误带入无关改动，或者越过子仓库边界修改父仓库。
- 自动清理旧版本后，用户失去本机快速回退能力。

因此，发布体系的核心目标不是缩短成一条命令，而是建立一条边界明确、结果可复核、失败后不会静默覆盖历史的发布事务。

## 核心设计

### GitHub Release 承载产物，当前仓库同时作为 Scoop bucket

GitHub Release 负责保存与 Git 标签对应的不可变 ZIP，Scoop manifest 只负责把通道映射到该附件及其 SHA256。这样，源码、版本标签、发布附件和包管理入口都可以追溯到同一仓库。

manifest 固定放在本仓库的 `bucket/` 目录，不再维护独立的 `scoop_bucket` 仓库。拆分独立 bucket 会引入第二个提交和发布时序，既增加跨仓库失败点，也无法为当前单一产品带来足够收益。

### 本地 Python 程序负责编排

发布入口采用 Python 标准库实现，由 [`publish_release.py`](../scripts/publish_release.py) 统一编排 Cargo、Git 和 GitHub CLI：

- `repo_debug` 的 release 构建依赖父 Cargo workspace，发布程序通过 `cargo metadata` 获取真实 workspace 和 target 目录，不假定调用时的当前目录。
- 路径处理、manifest 生成、ZIP 打包和 SHA256 计算使用 Python 标准库，避免增加仅为发布服务的第三方依赖。
- GitHub 认证完全交给 `gh`，发布程序不读取、不传递也不保存访问令牌。
- 复杂逻辑保留在可本地调试的普通脚本中，不把发布语义分散到难以复现的手工命令或 CI 配置里。

### stable 与 alpha 是两个 Scoop app

Scoop 没有独立的 channel 抽象，所以 stable 与 alpha 必须表示为两个 app，而不是让一份 manifest 同时追踪两类版本。

| 通道 | 版本形态 | Scoop app | Manifest | GitHub Release | 对外命令 |
| --- | --- | --- | --- | --- | --- |
| stable | `X.Y.Z` | `repo_debug` | `bucket/repo_debug.json` | 正式 Release | `repo_debug` |
| alpha | `X.Y.Z-alpha.N` | `repo_debug-alpha` | `bucket/repo_debug-alpha.json` | prerelease，且不标记为 latest | `repo_debug` |

两个 app 都将 `repo_debug.exe` 暴露为同一个 `repo_debug` shim。通道差异只存在于包管理层，不进入 CLI 名称，避免脚本、配置和用户习惯随着通道切换而变化。

代价是两个 app 同时安装时会竞争同名 shim。Scoop 通过最后一次安装、更新或 `reset` 的 app 决定当前入口，因此“已安装哪个通道”和“当前命令指向哪个通道”是两个不同状态。

## 发布约定

### 版本和命名

- 唯一版本来源是子仓库 `Cargo.toml` 中 `repo_debug` package 的版本。
- 只接受 stable 和 alpha 两类版本；无法归类的预发布版本必须停止，不能猜测通道。
- Git 标签固定为 `v<version>`。
- Windows 目标固定为 `x86_64-pc-windows-msvc`。
- 附件固定命名为 `repo_debug-v<version>-x86_64-pc-windows-msvc.zip`。
- ZIP 使用扁平结构，只包含 `repo_debug.exe`、`README.md` 和 `CHANGELOG.md`。
- 下载地址由标签和附件名确定，不使用可变的 latest 下载地址。

### Manifest

- 每次发布只生成和更新当前通道的 manifest，不触碰另一通道。
- stable 使用 Scoop 的 GitHub 正式 Release 检测；alpha 查询 GitHub Releases API，并只匹配 alpha 版本。
- 两个 manifest 都只描述各自通道的最新版本，不在仓库中维护历史版本清单。
- `version`、附件 URL、SHA256 和 `bin` 必须在写入前完成一致性校验。
- 尚未正式发布的通道不创建占位 manifest；`bucket/` 中不存在该文件就是“该通道尚未建立”的真实状态。

### 确定性产物

manifest 中的 SHA256 必须对应最终上传的 ZIP。为避免相同输入因本地文件时间和权限不同而生成不同哈希，ZIP 条目使用固定时间戳、权限、名称和顺序。上传完成后，发布程序重新下载 Release 附件并核对大小和 SHA256，而不是只相信上传命令成功。

### 仓库边界

- 子仓库负责版本、CHANGELOG、README、发布脚本、Scoop manifest、Git 标签和 GitHub Release。
- 父仓库只提供 Cargo workspace、锁文件、共享依赖和构建输出目录。
- 发布程序可以从子仓库定位父 workspace 并调用 Cargo，但所有 Git 写操作必须显式使用 `git -C <子仓库>`。
- 发布时只允许暂存目标通道的一个 manifest，禁止使用会顺带暂存其他文件的命令。
- 子仓库产生发布提交后，父仓库出现 gitlink 变化是正常结果；是否更新父仓库指针属于发布流程之外的独立决定。

### 回退和用户数据

- 发布、安装和升级流程不得自动执行 `scoop cleanup`。Scoop 保留的旧版本目录是快速回退能力的一部分。
- manifest 只负责未来更新，不保证从远端任意安装历史版本；主要回退边界是本机仍保留的版本。
- stable 和 alpha 共用的用户配置必须保持向后兼容，或者在发布说明中明确不可逆影响。
- `scoop reset` 只切换二进制和 shim，不会回滚用户数据。

## 发布事务与失败边界

正式发布按以下状态顺序推进：

1. 从 `Cargo.toml` 解析版本和通道，并从 CHANGELOG 提取对应发布说明。
2. 确认子仓库干净、当前分支已设置 upstream 且与远端完全同步，同时确认 Cargo、Git、`gh` 和 GitHub 登录状态可用。
3. 确认同版本的本地标签、远端标签和 GitHub Release 均不存在。
4. 从父 workspace 完成 locked release 构建，生成确定性 ZIP 和 SHA256，并校验目标通道 manifest。
5. 仅写入、暂存、提交和推送目标通道 manifest；若内容没有变化则复用当前 HEAD。
6. 在该提交上创建并推送版本标签。
7. 创建对应类型的 GitHub Release，上传之前生成并计算过哈希的 ZIP。
8. 重新查询 Release，并下载附件复核大小和 SHA256。

顺序本身是约定的一部分：manifest 必须先进入可追溯的提交，标签必须指向该提交，Release 和附件才能以这个标签为身份建立。

`--dry-run` 复用版本解析、构建、打包、哈希和 manifest 校验，但只在终端预览 manifest。它可以在 `.release/<version>/` 产生未跟踪的构建输出，不得修改受 Git 跟踪的文件，不执行提交、推送、打标签或 GitHub Release 操作。

失败处理遵循以下规则：

- 版本无法归类、仓库未同步或 CHANGELOG 缺失时，在任何发布写入前停止。
- 构建、打包或 manifest 校验失败时，不创建 manifest 提交和远端对象。
- manifest 提交或推送失败时，不继续创建标签和 Release。
- 本地标签、远端标签或 GitHub Release 任一已经存在，都将该版本视为已占用，禁止自动覆盖、补传或复用。
- 标签已推送但 Release 创建失败，或 Release 创建后的附件校验失败，都保留现场供人工判断；只有明确作废并完整清理 Release 与标签后，原版本才允许重试。
- 发布程序不自动回滚远端状态，因为无法证明失败前后的对象仍只由本次运行控制。

## 踩过的坑及原因

### 一份 manifest 不能表达两条更新轨道

Scoop manifest 只有一个当前版本和一套更新规则。如果 stable 与 alpha 共用 manifest，普通用户可能被带入预发布版本。两个 app 虽然带来 shim 竞争，但能保持更新轨道独立，风险更可见也更可控。

### GitHub 的 latest 与 prerelease 语义不能混用

stable 必须只追踪正式 Release；alpha 必须使用明确的版本过滤，并在创建 prerelease 时禁止其成为 latest。仅按“版本号更新”判断会让 stable 与 alpha 相互串线。

### ZIP 元数据也会改变哈希

即使二进制和文档内容不变，文件时间、权限或条目顺序不同也会改变 ZIP 字节和 SHA256。发布程序固定这些元数据，确保 manifest 哈希可以复现，并对远端实际附件做二次校验。

### 已存在的版本不能当作可恢复检查点

同一个版本可能只存在标签、只存在 Release，或者附件上传到一半。自动判断“缺什么就补什么”容易把不同运行产生的内容拼成一个发布，因此当前策略宁可报错，也不自动覆盖或续传。

### cleanup 与回退能力互相冲突

Scoop 的历史版本切换依赖本机仍保留的版本目录。自动 cleanup 虽然节省空间，却会悄悄删除最直接的回退点，所以清理只能由用户在确认不再需要回退后主动执行。

### 子仓库提交会传导为父仓库 gitlink 变化

发布程序只提交子仓库 manifest，但父仓库会观察到子模块 HEAD 改变。这不是发布程序越界修改父仓库；反过来，也不能因为父仓库显示变化就让发布程序顺手提交父仓库指针。

### Raw PowerShell 初始化器同时受编码和进程边界影响

README 通过 GitHub Raw 分发一次性 [`init_scoop.ps1`](../scripts/init_scoop.ps1)，让来源保持统一，并使安装后新增的 PATH 能在当前 PowerShell 进程立即生效。这个入口有三项必须长期保持的约定：

- 脚本必须保存为 UTF-8 无 BOM。`irm` 将响应解码为字符串后，BOM 会成为 `U+FEFF`，导致紧随其后的 `#Requires` 被 `iex` 当作未知命令。
- 顶层失败必须抛回调用方，不能使用 `exit` 主动结束承载脚本的用户终端。
- 环境变量只能影响当前进程及其后代。初始化器可以刷新它所在 PowerShell 的 PATH，但从独立子进程运行时无法反向修改父终端。

执行策略和 Windows 权限是两类问题：内存字符串执行不等于提权。初始化器仍需以普通用户权限运行，并为后续磁盘上的 Scoop PowerShell 脚本建立合适的 CurrentUser 执行策略。
